# Backend completion checklist — 2 November 2026

Authentication is implemented and owner reports successful deployed client login. That does not mean the marketplace backend is complete. Backend API modules currently present: auth and admin_users only. Other UI records, dashboard metrics, properties and operational journeys still use illustrative frontend data.

## Already implemented (awaiting remaining review/operational setup)

- PostgreSQL identity tables and migrations; seed admin (created in Neon).
- Client registration, shared role-based login, logout, current user, rotating refresh tokens.
- Eight-character minimum, Argon2id hashing, CSRF/Origin checks, session revocation, persistent rate limits.
- Database-assigned client/staff/admin access; admin account creation and activation controls.
- Reset, verification and invitation token APIs; private email outbox and SMTP sender abstraction.
- Audit append-only enforcement, policy consent/version records, health endpoint and consistent errors.
- FastAPI container and private environment setup; owner has deployed to Render.

## Remaining work by module

1. **Foundations:** complete schema/contract alignment; money type and validation; OpenAPI export/drift checks; CI with PostgreSQL, migrations, lint, typecheck and dependency audit; environment smoke checks.
2. **Authentication operations:** configure/test real email delivery, outbox scheduling/retries and reset/verification/invitation journeys; complete role/access review, concurrency and deployment checks; replace draft policies and version consent when ready. Do not recreate the seeded admin. Authentication is not to be rebuilt.
3. **Property database:** landlords, properties, location/district taxonomies, amenities, media, evidence documents, verification, approval and status histories; constraints, indexes and reversible migrations.
4. **Uploads/storage:** choose/configure object storage; photo, video and document APIs; file type/content, size/count validation; private ownership documents; scoped upload tokens, thumbnails, EXIF handling, signed access and failed-upload cleanup. Confirm video limits/processing in the shared contract before implementation.
5. **Landlord submissions:** public contact registration (no landlord account), draft/save/submit, scoped tokens, consent, ownership/authority evidence, anti-abuse controls and required-photo/document checks.
6. **Staff property operations:** queues/filtering, assignment, landlord directory, edits/version conflicts, media management, availability confirmation, verification records, owner price/description approval, publish/unpublish guards and audit history.
7. **Public browsing:** real property search/detail, taxonomy/filter options, pagination/sorting, published-only visibility, private-field exclusion, availability dates and query performance. Remove illustrative listings only once the live endpoints are connected.
8. **Inquiries/messaging:** property and general inquiries, duplicate/idempotency rules, client-owned threads, replies, staff pipeline/assignment/qualification, private internal notes, status history and client directory/deactivation. Connect account overview to actual user counts and empty states.
9. **Inspections:** scheduling, staff/property conflict detection, client confirmation, cancellation/rescheduling, outcomes, audit and exact-address disclosure only at the contract-defined stage.
10. **Fees/transactions:** versioned fee rules, integer-kobo arithmetic and rounding, rental/sale calculation bases, disclosure snapshots, transaction lifecycle, append-only ledger, manual payment records/reversals and client-only summaries. Payment gateway/webhooks/reconciliation remain deferred; no platform custody of funds assumed.
11. **Complaints/reports:** public reports and client complaints, evidence, anti-spam/duplicates, staff investigation, confidentiality, precautionary hold/review dates, findings/outcomes, admin-only permanent actions and reporter updates. Report counts must not automatically punish listings.
12. **Notifications:** event catalogue, recipients/templates, transactional outbox and scheduled worker, retries/backoff, delivery failures, inquiry/inspection/property/transaction events, in-app list/read state if adopted.
13. **Reporting:** documented KPI formulas, date-range aggregates, role restrictions and fixture-verified dashboards. Replace sample metrics with genuine aggregates.
14. **Availability maintenance:** configurable stale-listing threshold, scheduled flagging and staff reminders (Could priority).
15. **Support/assistant:** real support phone/hours/timezone config, public config, approved knowledge articles/admin publication, provider interface, public-only retrieval, deterministic handoffs and call option, budgets/rate limits, redaction/log retention, golden-set/injection/privacy tests. Assistant is Should priority and must not read private landlord/client records.
16. **Production readiness:** authorisation/privacy sweep, security/dependency review, request/file limits, logs without secrets/PII, performance/load/index tests, deployment migrations, rollback, backup/restore drill, retention/deletion jobs, monitoring/alerts, health checks and incident procedures.
17. **End-to-end integration/release:** real-stack tests per module, migration up/down on isolated databases, remove mocks per accepted module, staff UAT, policy/practice review, release checklist and post-release monitoring. Never run destructive tests against Neon application data.

## Recommended implementation order

Finish foundations and auth mail operations; then property schema → storage/uploads → landlord submission → staff verification/publication → public search/detail → inquiries/messages → inspections → transactions/fees → complaints → notifications/reporting. Assistant and optional automation follow the required marketplace journeys.
